DESIGN JUDGEMENT / FOUNDATION CONTRACT
A. INTERACTION TYPE IS FIRST-CLASS DATA
Each assessment item should declare an interaction type independent from subject matter, e.g.:
- single_select
- multi_select_unordered
- sequence_order
- match/pair
- categorize
- short_text / constructed_response
- numeric / formula where applicable
- hotspot/diagram where applicable
The domain content supplies prompt, choices/items, expected response/rubric, explanation, sources and metadata.

B. ORDERED PROCEDURE QUESTION — PREFERRED INTERACTION
For a strict ordered procedure, use a sequence/order interaction, not checkbox-style multi-select.
Preferred UI concept:
- prompt explicitly says `Put these steps in order` or equivalent;
- all candidate steps appear as readable cards/rows;
- selected/current sequence is visibly numbered 1, 2, 3...;
- learner can reorder via drag as an optional enhancement;
- every item also has accessible single-pointer/keyboard alternatives such as Move up / Move down and/or Choose position;
- order is visible before submission and remains inspectable after submission;
- feedback compares the learner sequence to the correct sequence and explains consequential ordering errors rather than dumping raw indexes.
If the learning objective is merely 'select all applicable parts' and order is irrelevant, use ordinary multi-select instead. Do not conflate the two constructs.

C. DOMAIN-AGNOSTIC ASSESSMENT ENGINE
The engine should reason about learning/assessment constructs, not professions. Examples:
- law: order procedural elements or stages of an analysis;
- forensics: sequence evidence-handling or analytical steps;
- engineering: order process/diagnostic steps;
- policing: sequence a lawful/procedural workflow when the course source genuinely defines an order.
The same renderer, scoring contract, accessibility behavior, attempt provenance and feedback-state machine should serve all of them.

D. CONTENT / LOGIC SEPARATION
Keep subject-specific terms, legal rules, formulas, facts and examples in course/item data. Keep interaction behavior, scoring primitives, confidence handling, feedback presentation, provenance, progress and accessibility in reusable domain-neutral components. A new course should primarily add content/configuration, not require rewriting core interaction logic.
