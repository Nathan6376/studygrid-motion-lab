NEEDS ARCHITECTURE DECISION
1. Instructor vs learner shell boundary
- Owner wants instructor mode to become a distinct instructor product shell; learner Study and learner-only navigation must not leak into instructor context.
- One account may have learner/instructor/owner capabilities, but capability must not equal always-visible mixed chrome.
- Define explicit role/context switching and what state/navigation should survive the switch.

2. Instructor demo → real setup transition
- Demo should use fake example classes and a short guided walkthrough with Skip.
- After the walkthrough, user should move naturally to real signup/setup rather than being trapped in a sandbox.
- Define durable separation between demo data/state and real authenticated data/state so no fake class can masquerade as a real class.

3. `Find current class`
- Owner wants a context-aware action that can use known institution/program/program-term/section/schedule context to surface the likely current class.
- Define safe basis/explanation/correction contract. Never fabricate certainty.
- Decide what counts as `current`: user-selected active class, time/calendar context, known schedule, or other verified signals; preserve manual correction.

4. Help / policy IA
- Owner wants Privacy Policy and other required policies/notices accessible from Help.
- Define product IA placement only; do not claim legal completeness. Identify which items are product-surface decisions vs legal/content dependencies.

5. Tutorial / progressive guidance state
- Decide where tutorial state lives, what is remembered, how replay works, and how contextual guidance retires after demonstrated use without becoming permanent clutter.
- Tutorial must never be required for core use.
- Define the semantic/state separation between: keyboard focus, selected/active state, tutorial target/spotlight, decorative adaptive-response emphasis, saved study highlight, hover and pressed state. The screenshot-confirmed blue box/halo failures show why these cannot share ambiguous styling/state.

6. Motion as shared product primitive
- Owner wants coherent animation language across Selectric/full-loop, instructor adaptive-response demo, contextual help reveals, ghost-cursor demonstrations and appearance showcase.
- Architecture should define shared motion-system boundary and state semantics, while Gemini/Research define choreography/evidence. Do not adjudicate exact easing/art direction beyond system-level constraints.
- Motion/decorative layers must not capture focus, alter navigation semantics, become the sole carrier of meaning, or attach selection/focus-looking chrome to noninteractive hero copy.

7. Decorative visual layer boundary
- Define whether decorative arcs/orbs/lines live in a nonsemantic presentation layer so they cannot interfere with focus, hit targets, reading order or tutorial target state.
- Decorative elements that cross instructional text or look like state indicators need explicit reject conditions.
- Preserve the liked StudyGrid orb/ball as an intentional branded primitive while preventing unrelated arcs/circles from becoming noise.

8. Practice-state hierarchy contract
- Architecture does not need to design the card, but it should define semantic separation between learner answer, correct answer, confidence selection, explanation/help, and completion state so Bob cannot collapse all of them into one visual/state container.
- `Skip` is an action distinct from a confidence value even if presented in the same interaction group; preserve that distinction in state and analytics semantics.
