WORKSTREAM D — PAGE/ROUTE TRANSITIONS + CONTEXTUAL NAVIGATION

CONFIRMED CURRENT PLATFORM STATE — WebKit’s Interop 2026 note says same-document View Transitions were a 2025 focus and cross-document View Transitions shipped in Safari 18.2; Interop 2026 expands/continues the cross-document work:
https://webkit.org/blog/17818/announcing-interop-2026/
CONFIRMED — prefers-reduced-motion is broadly available and communicates a user preference to reduce/replace nonessential motion:
https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/%40media/prefers-reduced-motion
CONFIRMED PLATFORM GUIDANCE — Apple Motion says custom motion should support status/feedback/instruction without excessive or distracting motion and platform interaction mode can appropriately change motion emphasis:
https://developer.apple.com/design/human-interface-guidelines/motion

TRANSITION CONTRACT — RECOMMENDATION
- Route correctness, history, focus and destination state MUST NOT depend on the animation API.
- Use View Transitions as progressive enhancement. Unsupported/reduced-motion path snaps or uses a minimal opacity change.
- Micro state change: ~120–180 ms.
- Section/deep-context change: ~160–220 ms.
- Major page/route continuity: ~180–260 ms; exceed ~300 ms only when the spatial explanation is genuinely valuable.
These are StudyGrid design ranges, not web standards.
- Shared-element movement only when the same conceptual object persists across views.
- Fade/crossfade for lateral content replacement without a meaningful spatial relationship.
- Short directional slide only for clearly ordered hierarchy/progression.
- Scale only for local element emergence/dismissal, not whole-page zooming.
- No spring/bounce/overshoot default, no animation queue backlog, no motion that delays interaction.

FOCUS / HISTORY / ACCESSIBILITY CONTRACT
- Destination gets a correct page title/landmark and focus strategy; do not leave focus trapped in removed source UI.
- Browser Back and keyboard navigation must work identically with animation disabled.
- Reduced motion removes large spatial translation/rotation rather than merely slowing it.
- Interrupting/navigating again cancels or safely supersedes in-flight animation.

CONTEXTUAL CHROME
RECOMMENDATION — in deep study, quiet nonessential chrome but retain: current class/location, a reliable Back/escape, and an obvious way to restore full navigation. Do not hide orientation or recovery merely to gain visual minimalism.

REJECT CONDITIONS
Latency added purely for flourish; focus loss; history mismatch; scroll reset without intent; stale destination title; motion continues after new navigation; required controls hidden during transition; reduced-motion still performs large spatial motion.

WORKSTREAM E — SATISFYING BUT RESTRAINED COMPLETION MICROINTERACTIONS

CONFIRMED GUIDANCE — Apple Motion supports motion as status/feedback; Apple Undo/Redo stresses predictable reversal and showing the result of undo/redo:
https://developer.apple.com/design/human-interface-guidelines/motion
https://developer.apple.com/design/human-interface-guidelines/undo-and-redo

RECIPE 1 — MARK REVIEWED
RECOMMENDATION: local 140–200 ms check/stroke/fill settle inside the existing control; subtle label/state change; no row jump; preserve focus. Optional small status message only if the change is otherwise easy to miss.

RECIPE 2 — MARK RESOLVED
RECOMMENDATION: 160–220 ms local emphasis/settle, then the item remains spatially intelligible before any filtering/removal. If the action changes list membership, keep a short reversible status/Undo affordance tied to the exact item.

RECIPE 3 — UNDO
RECOMMENDATION: restore the exact prior object/state, visually identify what returned, and preserve deterministic focus. Avoid generic “Undone” when multiple actions could plausibly be targeted.

REJECT CONDITIONS
Confetti, streak counters, oversized celebration, looping pulse, springy reflow, whole-page motion for a local completion, hidden result, duplicate Undo history or web-haptic dependency. Browser/web haptics are not part of the acceptance contract.

WORKSTREAM F — IPAD/SAFARI CURSOR, TEXT SELECTION, MARKING OVERLAYS + AUTOFILL

CONFIRMED CURRENT PLATFORM FACT — MDN states iPadOS supports pointer devices and the default pointer is a circle; `text` is the cursor value that changes its appearance:
https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/cursor
Therefore StudyGrid’s broad `.annotatable-text { cursor:text; ... }` is a direct, evidence-backed likely cause of the owner-observed I-beam when using an iPad trackpad/mouse.

CONFIRMED CURRENT WEB FACT — `user-select:text` makes text selectable; its initial value is `auto`:
https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/user-select
Thus text selection does not require forcing `cursor:text` over every broad reading container.

RECOMMENDED MITIGATION
- Remove broad `cursor:text` from passive reading containers unless the interaction deliberately needs a text-edit/select cursor cue.
- Preserve native selection with `user-select:auto`/default where possible; use explicit selection constraints only when required by the annotation interaction.
- Scope any marking cursor/overlay to the active marking mode and exact target surface.
- On cancel, submit, route change and component unmount, teardown overlay, pointer listeners/capture, selection styling and transient cursor classes. Stale crosshair/pointer state is a release reject.

SELECTION UX
Touch long-press/native selection should remain possible for study text that is meant to be copied/selected. Annotation tools must not permanently suppress the browser selection model. If a custom selection popover exists, its dismissal cannot destroy the user’s underlying text/navigation state unexpectedly.

CONFIRMED SAFARI AUTOFILL LIMIT — Apple says Safari uses multiple webpage signals for AutoFill and explicitly ignores `autocomplete="off"`, leaving AutoFill control to the user’s Safari settings:
https://developer.apple.com/documentation/safari-developer-tools/autofill
CONFIRMED WEB SEMANTICS — valid autocomplete tokens are standardized; made-up tokens are not a sound workaround:
https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/autocomplete

COURSE-SEARCH RECOMMENDATION
- Use a real search/text control with label and name/ID describing course search, course code or class code — not person/name/contact semantics.
- Do not invent `autocomplete="course"` or random invalid tokens.
- Treat `autocomplete="off"` as non-guaranteed in Safari.
- Keep product-generated suggestion lists semantically separate from browser AutoFill.
- Verify on real iPad Safari with AutoFill/contact data enabled.

https://www.w3.org/WAI/ARIA/apg/patterns/button/

CONFIRMED LINK GUIDANCE — W3C Link Purpose requires links to communicate their destination/purpose sufficiently:
https://www.w3.org/WAI/WCAG22/Understanding/link-purpose-link-only.html

STUDYGRID CONTROL CLASSIFICATION — RECOMMENDATION
- HISTORY BACK: restore browser/SPA prior entry and meaningful prior state; label `Back` when unambiguous.
- HIERARCHY PARENT/UP: deterministic parent destination; label it explicitly, e.g. `Classes` or `Back to Classes`; do not pretend it is browser history.
- EXPLICIT DESTINATION: link/navigation control named for the destination, e.g. `Open class`, `Profile`.
- LINEAR PROGRESS: `Continue`/`Next` only when the path is genuinely ordered and the destination is predictable from the flow.
- COMMAND: native button semantics for `Mark reviewed`, `Save`, `Resolve`, `Submit feedback`.
- REVERSIBLE MUTATION: command + clear result and exact Undo/recovery where appropriate.

ROUTE/BUTTON AUDIT RUBRIC FOR STUART
For every actionable control assert:
1. visible label matches actual destination/action;
2. semantic element/role matches link vs command;
3. enabled/disabled state is truthful;
4. keyboard activation and focus order work;
5. Back category is declared and behaves accordingly;
6. prior scroll/selection/form state is preserved when history semantics promise it;
7. parent-route controls do not accidentally depend on browser history;
8. Next/Continue is absent where the journey branches or destination is ambiguous;
9. reversible mutation exposes the intended recovery path;
10. destination title/heading/focus confirms where the user arrived;

12. same assertions pass with route motion disabled/reduced.

CONFIRMED WEB CAPABILITY — CSS `transform-style: preserve-3d` supports children positioned in 3D space:
https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/transform-style
CONFIRMED WEB CAPABILITY — `Element.animate()` is broadly available and returns a controllable Animation:
https://developer.mozilla.org/en-US/docs/Web/API/Element/animate
CONFIRMED ACCESSIBILITY PRECEDENT — W3C carousel guidance requires user control over animation, keyboard operability, sensible focus and pause/stop capability for moving content; its animation guidance calls for pausing on hover/focus when autoplay exists:
https://www.w3.org/WAI/tutorials/carousels/
https://www.w3.org/WAI/tutorials/carousels/animations/
CONFIRMED REDUCED-MOTION SUPPORT:
https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/%40media/prefers-reduced-motion

RECOMMENDED IMPLEMENTATION FAMILY — RESEARCH ONLY
For three short textual states, prefer semantic DOM/native text + CSS 3D transforms with Web Animations API orchestration. Canvas/WebGL is disproportionate unless later requirements demand true mesh lighting/geometry that DOM transforms cannot provide; DOM keeps text semantics/sharpness/debuggability simpler.

MOTION CONTRACT
- One implied rotor/typeball axis; do not render or choreograph a globe.
- Three stable readable message states at rest.
- Each transition follows one shortest coherent compound path; no random Euler wobble or contradictory axes.
- No 360° show-off spin between adjacent states; no blur-heavy smear; no bounce/spring.
- Prototype timing recommendation: roughly 450–650 ms for the compound state transition. If autoplay exists, a 4–6 s dwell is a reasonable test range; this is a design range, not a standard.
- Safer welcome behaviour: one bounded introductory cycle and stop, OR explicit next/previous/pause controls. Endless autonomous looping is rejected.
- Hover/focus pauses any continuing autoplay; user controls remain keyboard-operable.
- Preserve primary Sign in/hero hierarchy; motion is supporting identity, not a task gate.

SEMANTICS
- Keep one stable semantic representation of the message set (e.g. labelled text/list/status context) independent of the decorative transformed copies.
- Decorative duplicate faces may be `aria-hidden` only when equivalent semantic text remains available.
- Never hide the only meaningful interactive control from assistive technology.
- Do not spam live-region announcements on every visual rotation.

REDUCED MOTION
No spatial typeball rotation. Show a static message/list or perform an instant/very small opacity state change. “Reduced” must not mean “same spin, slower.”

REJECT CONDITIONS
Globe metaphor; perpetual spin; 360° flourish; text unreadable while moving for long periods; motion required to access meaning/action; focus moves with decorative faces; no pause for autoplay; reduced-motion still rotates; Canvas/WebGL chosen without a material visual requirement; Safari/iPad transformed text appears soft/jittery in physical-device QA.
