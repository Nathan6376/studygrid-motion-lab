1. INFORMATION ARCHITECTURE — ADOPT WITH BOUNDARY CLARIFICATION
A. FIRST-RUN / SCHOOL CONTEXT SETUP owns persistent user-level academic context:
1) Institution — searchable curated selection; explicit "My school isn't listed" manual fallback.
2) Program / credential — institution-scoped selection; manual fallback only when unavailable.
3) Current PROGRAM TERM — Term 1 / Term 2 / Term 3 / Term 4 / Other.
4) Join-code branch — ask whether an instructor supplied a class/join code. If yes, code-first enrolment is the primary path and bypasses manual class creation/course selection where the code resolves successfully. If no, continue to course selection.
The school/program/current-program-term context is persisted at profile/school-context level and editable later from Settings/Profile. It is not re-requested on every Add Class flow.

B. ADD CLASS AFTER SETUP owns class enrolment/creation only:
- Primary surface: searchable course picker scoped by the persisted institution + program context.
- Search accepts course title or code and resolves one canonical course identity.
- Current program-term-relevant courses are ranked/shown first; an explicit All Courses/search-beyond-term path remains available.
- Program prefix is contextual/implicit when already known. UI may show "207" while canonical storage remains the verified full official code such as "PFP 207" only when that official identity has actually been verified.
- Manual Add remains a secondary explicit fallback, visually and semantically distinct from verified catalogue selection.
- Add Class must not repeat institution/program/program-term fields unless the user intentionally invokes a context override/change.
- Course-name fields must use course/search semantics and be tested against the owner-relevant Safari/iPad browser class; autocomplete markup alone is not accepted as proof that personal-name autofill is fixed.

C. SETTINGS / PROFILE owns changing persistent school context. Changing institution/program/current program term is a context change, not an ordinary per-class edit.

2. PROGRAM TERM VS ACADEMIC SESSION — KEEP THEM ORTHOGONAL
Architecture decision: PROGRAM TERM and ACADEMIC SESSION are different dimensions and must never share one field or label.

PROGRAM TERM
- Meaning: progression position inside the program.
- Canonical values for the current owner requirement: TERM_1 | TERM_2 | TERM_3 | TERM_4 | OTHER.
- If OTHER is selected, a separate manual label/value may be stored.
- This is the control that replaces the current free-text "Fall 2026 / Winter 2027 / Summer 2027" Term field.

ACADEMIC SESSION
- Meaning: calendar/session occurrence used when needed for offerings, scheduling or historical placement (for example a Fall/Winter/Summer-labelled session if the institution uses one).
- Store separately as academic_session_id plus display metadata supplied by a verified source or explicit manual context.
- Do not expose it as the primary "Term" selector in the redesigned onboarding.
- The local prototype may omit the academic-session selector from the main path until a real use case/source requires it; it must not fake session data by stuffing seasons/years into program_term.

3. DATA MODEL — ACCEPTED MINIMUM SEPARATION
Persistent school/profile context:
- institution_id — canonical StudyGrid identity for the selected institution; display name is separate.
- program_id — canonical StudyGrid identity for the selected program/credential, scoped to institution.
- program_prefix — contextual program/course prefix where verified (for example PFP); not the user's primary typed course-code field.
- program_term — TERM_1 | TERM_2 | TERM_3 | TERM_4 | OTHER.
- program_term_other_label — nullable; only for OTHER.
- academic_session_id — nullable/separate; never aliases program_term.

Verified catalogue read model:
- catalogue_course_id — canonical StudyGrid course metadata identity.
- institution_id.
- program_id / applicable_program_ids.
- canonical_course_code — full official code exactly as verified from the official source.
- display_course_number — presentation convenience only, derived/contextual when safe; never replaces canonical_course_code as identity.
- course_title.
- program_term applicability metadata where the official source supports it; absence must remain unknown rather than fabricated.
- source_url / source reference.
- source/snapshot version identity.
- last_verified_at.
- verification/provenance status sufficient to distinguish verified official data from manual/local fallback.

Class/enrolment identity:
- class_section_id — StudyGrid class/section instance identity; separate from catalogue_course_id.
- join_code — instructor/class-issued enrolment identity that resolves to a class_section_id; it is not a course-catalogue ID and must not be used as one.
- A manually added class/course is marked manual/unverified and must not masquerade as verified catalogue metadata.

4. OFFICIAL-CATALOGUE SOURCE MODEL — APPROVED ARCHITECTURE, RESEARCH GATE REQUIRED
- Official institutional websites/catalogues and supported official endpoints are the only allowed sources for verified institution/program/course metadata under this owner requirement.
- No institutional catalogue entry may be presented as verified merely because it is plausible, present in a local prototype, or inferred from the owner's examples.
- Research must first map which current official sources/endpoints actually exist, their fields/stability, and a viable refresh/update strategy. This packet does not claim any specific institution source availability because the consumed route does not verify it.
- Runtime Add Class must read from a local/backend catalogue snapshot/read model; do not place live web scraping in the critical click path if avoidable.
- Every verified snapshot requires provenance/version/last-verified evidence and graceful unavailable/ambiguous fallback.
- Later backend ingestion may normalize official sources into canonical IDs, but the UI contract must not depend on one specific scraping implementation.
