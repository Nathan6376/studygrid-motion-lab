BOTTOM LINE
All owner-requested product directions in this tranche are implementable inside the current single-file architecture, but the current full-root/full-course-shell render pattern is the main technical source of physical instability. CURRENT SOURCE ARCHITECTURE — MATERIAL FINDINGS
1. ROUTING / HISTORY
- The app already has a small hash router: routePartsFromValue(), routeContextFromParts(), sameRouteContext(), nav(), parseRoute().
- nav() records route scroll/anchor when current/next routes share a route context, then changes location.hash (or replaceState for replacement navigation).
- handleRouteHistoryChange() listens to hashchange + popstate, closes route overlays, calls render(), focuses the route entry for cross-context changes, then restores scroll/anchor for same-context changes.
- This is usable infrastructure; it does not need to be replaced merely to improve UI stability.

2. FULL REMOUNT IS THE MAIN INSTABILITY SOURCE
- render() dispatches the whole root to Welcome, Tour, Start, Course, Plan, Access, Profile, Workspace or Courses.
- renderCourseRoute() reconstructs the complete .course-shell (course rail + course identity + course nav + #courseMain) on course-route changes, then renders the selected view.
- Therefore a sibling route change can recreate persistent chrome even when the user perceives it as the same workspace. That is the right architectural target for owner-reported layout/target movement.

3. THERE IS ALREADY A GOOD PARTIAL-UPDATE PRECEDENT
- Study Learn/Test/Support links already special-case same-workspace switching: history.pushState(), direct renderStudyStart(c,nextView), explicit keyboard-focus restoration and scroll restoration.
- That proves a persistent-shell/outlet pattern can be introduced incrementally without replacing the whole router.

4. STATE IS SUFFICIENT FOR A STABLE SHELL
- The current local state already carries activeCourseId, lastLearnerRoute, previewPersona, demoSignedIn, currentSession, lastSummary, questionReviews, studyHistory, coinBalance/coinAwards, localClasses and onboarding state.
- Persistence is already split into prefs / learn / support / feedback / telemetry namespaces.
- No backend is required to prototype a stable signed-in shell, context model, review terminal state, or automatic local reward state.

5. LATE OVERRIDES INCREASE REFACTOR RISK
- The file contains base renderers plus later sgBase* captures/overrides (render, renderStudyStart, renderSessionSummary, renderInstructorWorkspace, QB17R welcome, etc.).
- Future implementation should consolidate the chosen seam rather than add another broad late override layer; otherwise route/focus/state behavior becomes harder to reason about and test.

6. STUDY SETS: THE LAST-ITEM NO-OP IS EXPLAINED IN SOURCE
- Study Sets already has revision-bound review keys and states needs_review / approved / needs_changes / held, with set-level Draft / Needs review / Ready / Published / Held.

7. REWARD / SEEDS IS CURRENTLY A MANUAL TWO-STEP COMMIT

ARCHITECTURE OPTION A — PERSISTENT SIGNED-IN APP SHELL + ROUTE OUTLET
Shape:
- Keep the existing hash/History deep-link model.
- Split rendering into stable zones: Public/Onboarding shell and Signed-in shell.
- Signed-in shell mounts persistent global/context chrome once; route changes update a main outlet and only the context pieces that truly changed.
- Introduce a small route descriptor, e.g. zone(public|onboarding|signed-in), persona/role, courseId, surface, relation(parent|child|sibling), focusPolicy, scrollPolicy.
- A signed-in Home/current-workspace route can be represented without letting product Back controls walk into /start or public onboarding. Sign out remains the explicit exit.

How it handles the requested surfaces:
- Global vs local nav: one persistent app-level nav; course/context nav lives within the signed-in shell and is reduced when redundant.
- Sibling changes (Learn/Test/Support, instructor tabs): update outlet, preserve shell + control positions + relevant anchor/focus.
- Parent/child changes (Home→course, Study→lesson): update context/outlet; focus new heading when semantic context changes.
- General/self-directed study: represent it as a signed-in workspace context with courseId=null rather than as a separate public/onboarding branch.
- Role: route descriptor carries learner/instructor/general-study context; expose one compact stable context marker rather than stacking banners.

Risk / blast radius / reversibility:
- Implementation risk: MEDIUM.
- Blast radius: MEDIUM because render()/renderCourseRoute() and shell ownership change, but local feature state can remain intact.
- Test burden: HIGH on route/back/focus/scroll matrix, but coherent rather than special-case-heavy.
- Reversibility: GOOD if introduced behind a render adapter and migrated surface-by-surface.
- Primary benefit: directly attacks the repeated full-shell remount that causes target movement and duplicated chrome.

ARCHITECTURE OPTION B — TARGETED “ROUTE ISLANDS” ON THE CURRENT RENDERER

- Add targeted partial-render paths only for high-friction same-workspace transitions: Study modes, instructor tabs, Study Sets review, selected class/context controls, completion panels.

How it handles the requested surfaces:

Risk / blast radius / reversibility:
- Implementation risk: LOW–MEDIUM.
- Blast radius: LOW per slice.
- Test burden: MEDIUM initially, rising over time as more special cases accumulate.
- Reversibility: VERY GOOD.
- Main downside: long-term complexity; it can become a collection of exceptions around an architecture that still remounts too much.

ARCHITECTURE OPTION C — INTERNAL ROUTE/CONTROLLER LAYER INSIDE THE SINGLE FILE
Shape:
- Introduce a route table and controller lifecycle (mount/update/dispose) while keeping the product a single-file app.
- Persistent shell owns global delegated events. Each major surface owns an outlet/controller and updates state without recreating unrelated DOM.
- The current hash/History router can remain the compatibility transport initially; a Navigation API adapter can be optional later.

How it handles the requested surfaces:
- Explicit route metadata makes signed-in/public boundaries, roles, parent/child/sibling semantics, Back behavior, focus policy and scroll policy first-class rather than inferred ad hoc.
- Review/workflow state machines become controllers with terminal states rather than markup side effects.
- Cleaner long-term basis for general study + class study + instructor context.

Risk / blast radius / reversibility:
- Implementation risk: HIGH initially.
- Blast radius: HIGH if done as one rewrite; should only be considered as staged migration.
- Test burden: HIGHEST up front.
- Reversibility: MODERATE unless the old renderer remains behind an adapter during migration.
- Long-term benefit: strongest separation of route, state, DOM ownership and transition policy.

BROWSER / PLATFORM PRIMITIVES — FEASIBILITY
A. View Transition API
- Same-document document.startViewTransition() is now a practical progressive enhancement: Safari added View Transitions in Safari 18.0; MDN marks same-document startViewTransition Baseline 2025 across latest browsers.
- Use only behind feature detection. Correctness, focus, route state and layout must work identically without it because older iPads/Safari remain plausible.
- Good fit: sibling outlet swaps where the shell remains stable, selected-class or persistent-control continuity, modest cross-fades/slides.
- Poor fit: making every state change a page transition or relying on captured snapshots for focus/semantic behavior.

B. Navigation API
- MDN marks Navigation API Baseline 2026 on latest browsers, but WebKit’s Interop 2026 work still targets interoperability and Safari 26.3 continued adding Navigation API behavior.
- Therefore it is viable as a later adapter, NOT a core requirement for this tranche. The current hash/History router should remain the fallback/correctness path until physical supported-device QA proves parity.

C. Web Animations API (WAAPI)
- Safe as the primary controlled imperative animation primitive for this app; Safari has shipped Web Animations since Safari 13.1 / iPadOS 13.4.
- The app already uses Element.animate() and has a TourMotion primitive with direction, race/coalescing, focus behavior and reduced-motion handling.
- Reuse that discipline for bounded sibling transitions; do not indiscriminately animate layout.

D. CSS transitions
- Best for local visual state: hover/focus/pressed/state-emphasis, opacity/transform of contained controls.
- Avoid height/position animations that move unrelated targets. Prefer fixed/reserved geometry or outlet snapshots.

E. FLIP / shared-element techniques
- Feasible, but not needed as the default. Use only if a later selected design has a true shared element whose continuity materially improves orientation and View Transitions cannot provide the effect.
- Manual FLIP increases measurement/compositing and Safari/iPad QA burden; keep it exceptional.

F. Scroll/focus/history
- history.scrollRestoration is widely available. The existing app already has route-anchor and manual scroll helpers; preserve/refine them.
- Focus policy should be semantic: sibling transition retains triggering control where useful; parent/context transition focuses the new route heading; modal/dialog restores trigger; browser Back restores logical anchor without forced page-top unless context changed.

ACCESSIBILITY / MOTION CONTRACT
- Motion must never carry essential meaning alone.
- Keep prefers-reduced-motion and StudyGrid less-motion as hard gates.
- Moving Welcome visual remains AT-hidden with a stable semantic summary.
- Auto cycling pauses on focus and real pointer/touch/keyboard interaction; do not resume in a way that fights an engaged user.
- Keep route changes out of aria-live spam. Announce only concise outcome/context where needed.
- Never remove keyboard focus visibility to solve the owner’s green-square complaint.

FOCUS TREATMENT FEASIBILITY
Current source has a broad 3px outline plus multiple local focus-visible styles. The family can be centralized without reducing accessibility:
- one focus token set (color, outer contrast ring, offset/width);
- rounded controls use a radius-aware outer ring/box-shadow or outline strategy that follows component shape;
- :focus-visible gates keyboard-style focus so pointer clicks do not leave unnecessary square treatment;
- forced-colors/high-contrast fallback retains a real outline.
This should be a family-level refactor, not one selector at a time.

LEARNER STUDY WORKFLOW — SIMPLIFIED STATE MODEL
A technically clean future flow can be represented without inventing more routes:
1. ORIENT / TEACH — why this item matters, source/context, short teaching material where needed.
2. PRACTISE — answer interaction (single or multi-select).
3. OPTIONAL CONFIDENCE — subordinate, not a full visual takeover unless selected design requires it.
4. FEEDBACK — outcome + concise explanation/source; deeper tools secondary.
5. ADVANCE — stable Next/Finish target.
6. COMPLETE — accomplishment + what changed + recommended forward next step.

Assessment is a policy variant: response is stored but feedback is deferred until completion. Pause/resume is orthogonal session state, not a new study mode.

This separates “what am I doing?” from “how long do I have?” and avoids treating Quick/Focused/Deep labels as the product model. If duration remains, it can parameterize a selected study job rather than masquerade as three different jobs.

AUTOMATIC SEEDS — TRANSACTION SHAPE
- Reuse the existing deterministic milestone key so a reward cannot be duplicated.
- During finishSession(), compute reward; if key is absent, add award + balance + summary state together, then persist once.
- If persistence succeeds: completion UI says Seeds were added automatically; animation is secondary acknowledgement only.
- If persistence fails: roll back the local award/balance and show a truthful pending/unavailable state. Do not require “Collect” and do not claim the reward was saved.
- This remains local-only until a future connected backend has an authoritative transaction service.
