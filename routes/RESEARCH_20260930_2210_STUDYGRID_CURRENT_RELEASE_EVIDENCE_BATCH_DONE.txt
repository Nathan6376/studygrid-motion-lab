STUDYGRID TRANSITION CONTRACT — RECOMMENDATION
- Feature-detect `document.startViewTransition`; if unavailable/fails/reduced-motion, update instantly/correctly.
- Local hover/press/check/toggle: 70–120 ms.
- Local content reveal/filter/small panel: ~110–150 ms.
- Same-context card→detail/shared object: ~150–240 ms using shared-element continuity only when it is genuinely the same object.
- Parent/child route: ~180–240 ms with small directional translation + fade if hierarchy is spatially meaningful.
- Unrelated top-level route: 110–200 ms cross-fade; no fake directional slide.
- Large special transition: target 240–320 ms first; exceed ~400 ms only if owner-tested motion itself carries meaning. Never make routine navigation wait for decorative animation.
- Easing: restrained productive entrance/standard/exit curves; no spring/bounce/overshoot for routine StudyGrid navigation.
- Shared-element is rejected when the source/target are not the same conceptual object.

RECIPE 1 — MARK REVIEWED
- immediate 90–120 ms checkmark/check-stroke or icon state;
- 110–150 ms subtle tint/settle on the exact row/card; no confetti, bouncing or page-wide animation;
- text/status becomes “Reviewed” so colour/motion are never sole indicators;
- preserve item in place long enough for the learner to understand what changed.
Reduced motion: instant check + text/tint only.

RECIPE 2 — MARK RESOLVED + UNDO
- 90–120 ms local acknowledgement;
- if the active queue removes the item, use a restrained ~150–240 ms settle/collapse after the acknowledgement, while keeping resolved history accessible;
- surface one contextual `Resolved · Undo` control at the owner-requested lower-right/bottom relevant surface. Prefer a control that persists until the next meaningful resolution/navigation rather than an aggressive short timeout that disappears while the user is reading;
- Undo restores the exact item, original order/state and history relationship; it must not clone or regenerate the item.
Reduced motion: instant state move + status message.

RECIPE 3 — UNDO RESTORE
- brief 110–150 ms local restore highlight/opacity settle on the restored item;
- announce a polite status such as “Restored <item>”; do not steal focus unless the restored content must become the next task;
- do not replay the full forward animation backwards if that makes the interface feel theatrical.

AUDIO/HAPTIC RECOMMENDATION
No sound or vibration in the baseline web experience. If a future native wrapper supports high-quality haptics, treat them as optional complementary feedback bound to discrete actions, never required meaning.

LIKELY STUDYGRID CAUSE — EVIDENCE + SOURCE INSPECTION INFERENCE
The owner build applies `.annotatable-text { cursor:text; user-select:text; ... }` to lesson paragraphs, note bullets and quiz explanations. RECOMMENDED MITIGATION
- Preserve normal text selectability using standard browser behaviour / `user-select:auto` or narrowly scoped text selection.
- Do not force `cursor:text` on broad lesson/note/card containers. If a special selection affordance truly needs it, attach it only to the exact text region while the relevant feature is active.
- Selection popover appears only for a non-collapsed selection wholly inside whitelisted study content; anchor to the Range geometry and dismiss on selection collapse, route change, outside pointer/touch, Escape and invalidated content.
- Never block native touch long-press/copy selection merely to force a custom annotation UX.

FEEDBACK-MARKING TEARDOWN CONTRACT

- release any pointer capture;
- remove crosshair/pointer mode classes;
- remove overlay hit targets and route-level listeners;
- restore normal `touch-action`/selection/cursor rules;
- clear pending selected region/annotation state unless intentionally persisted.
Stale marking mode after exit is an acceptance failure.

COURSE-SEARCH AUTOFILL CONTRACT

STUDYGRID ROUTE/BUTTON AUDIT RUBRIC
For every actionable control record:
1. `control_id / visible_label / accessible_name`
2. control class: HISTORY_BACK | PARENT_UP | EXPLICIT_DESTINATION | FORWARD_NEXT | OPEN_CONTEXT | LOCAL_COMMAND | REVERSIBLE_MUTATION | DESTRUCTIVE_MUTATION
3. source route/state
4. expected destination/state
5. actual destination/state
6. history-stack effect
7. state to preserve: filters/scroll/selection/draft/focus/class context
8. keyboard/touch behaviour
9. focus after action
10. recovery/Undo semantics if state mutates

RULES
- HISTORY_BACK: uses meaningful prior app history and restores the last-seen state when possible. Direct-entry/no-meaningful-history needs an explicit safe fallback.
- PARENT_UP: routes to the product hierarchy parent and should say where appropriate (`Back to Classes`, class name, etc.) rather than pretending to be browser history.
- EXPLICIT_DESTINATION: label names/predicts its target; `Profile`, `Classes`, `Study` never rely on a generic Back icon to change meaning.

- DESTRUCTIVE/irreversible: confirmation only where consequence merits it; do not force confirmations for easy-to-undo routine actions.

WORKSTREAM H — WELCOME “FULL LOOP” TYPEBALL / 3D SELECTOR

EVIDENCE / PLATFORM CONSTRAINTS
CSS 3D is mature:
https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/perspective
https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/transform-style
https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/transform-function/rotate3d
`perspective`, `preserve-3d`, transforms and `rotate3d()` are widely available and allow real DOM faces to occupy/rotate in 3D space.

Web Animations API:
https://developer.mozilla.org/en-US/docs/Web/API/Web_Animations_API
https://developer.mozilla.org/en-US/docs/Web/API/Element/animate
Widely available playback/timing controls make pause/reverse/reduced-motion handling straightforward while keeping semantic DOM text.

Canvas accessibility tradeoff:
https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/canvas
Canvas does not expose semantic content to accessibility tools like HTML; it requires separate fallback/semantic handling. WebGL uses the same canvas boundary and is excessive for three short text faces unless true 3D mesh/material effects later become essential.

W3C carousel precedent:
https://www.w3.org/WAI/tutorials/carousels/
https://www.w3.org/WAI/ARIA/apg/patterns/carousel/
Auto-rotating one-at-a-time content needs keyboard-operable controls and user control over movement; screen-reader visibility must match what is actually shown.

Apple Reduced Motion evaluation:
https://developer.apple.com/help/app-store-connect/manage-app-accessibility/reduced-motion-evaluation-criteria
Spinning, depth simulation and auto-advancing content are specifically called out as motion that may need to stop/change under Reduce Motion.

RECOMMENDATION — NOT FINAL IMPLEMENTATION
Use a semantic DOM rotor, not Canvas/WebGL, for the first prototype:
- one compact rotor container with CSS `perspective` and `transform-style: preserve-3d`;
- three text faces positioned around one virtual axis/typeball shell;
- animate only the rotor transform with WAAPI/CSS transform; faces remain actual HTML text;
- visible item has normal contrast and reading orientation; hidden/back faces are visually hidden and removed from the accessibility tree/interaction until active;
- one stable accessible group label such as “StudyGrid loop” and explicit next/previous controls if the user can manipulate it;
- if labels themselves are navigation choices, each active face becomes a real link/button with destination-specific accessible name. Do not make off-axis hidden faces keyboard-focusable.

AUTOPLAY CONTRACT
Best default for StudyGrid: a short bounded demonstration, not an endless spinner. On initial welcome it may rotate through the three messages once, then settle. If General/owner chooses continuous auto-rotation, it must include pause/stop and pause on focus/interaction; do not rely on users reading moving text indefinitely. User interaction should immediately take priority over autoplay.

MOTION STARTING VALUES — OWNER-QA INFERENCE
- each 120° face change: ~220–320 ms, restrained ease-in/out; enough to perceive physical continuity but not enough to become a spectacle;
- dwell long enough to read the active label; do not rotate while the pointer/keyboard focus is inside the control;
- no wobble, spring or multi-axis orbit; one coherent axis like a typeball/Selectric head;
- perspective moderate; text should not become tiny/skewed for long portions of the cycle.
Exact timing is art-direction/QA, not a platform standard.

REDUCED-MOTION ALTERNATIVE
When `prefers-reduced-motion: reduce`:
- no 3D spin/depth traversal;
- show the three-step meaning statically (for example active text with quiet next/previous, or three compact labels) OR cross-fade one-at-a-time without spatial movement;
- retain the same information/destinations and keyboard semantics.

WHY CSS DOM + WAAPI WINS THIS PARTICULAR ELEMENT
- preserves crisp live text and native semantics;
- minimal GPU/asset/pipeline burden;
- easy to stop, scrub, skip and reduce;
- naturally responsive to text/font changes;
- progressive fallback is simple.
Use Canvas/WebGL only if later owner direction requires real surface lighting/mesh deformation that cannot be represented convincingly with CSS 3D. That would need a separate semantic control layer and additional iPad/Safari performance QA.

WELCOME SELECTOR REJECT CONDITIONS
- endless rotation with no pause/control;
- reduced-motion still spins/scales in depth;
- hidden faces remain focusable/announced as though visible;
- text becomes unreadable during most of the dwell cycle;
- Canvas/WebGL adopted only for novelty while duplicating DOM semantics;
- rotor blocks Sign in or delays first-use path;
- motion implies the three messages are buttons when they are not, or vice versa.
