BOTTOM LINE
======================================================================

Draft 1 is conceptually much safer than Draft 0, but it is NOT implementation-safe if engineers turn every named concept into a durable table/service and literally persist every layer.

The dominant implementation risk is now the opposite of Draft 0:
- Draft 0 collapsed epistemically different things.
- Draft 1 separates them correctly in prose, but can be over-normalized into duplicate durable state, generic graph edges, overlapping version systems and replay machinery that disagree with one another.

The smallest safe implementation is NOT “one table/service per Draft-1 noun.”
It is one deployable application with a small number of hard boundaries:
1. authority/catalog definitions;
2. immutable learner observations + append-only score artifacts;
3. derived inference/read models;
4. a pure next-action decision function + durable decision record;
5. product/application execution;
6. derived instructor views.

Draft 1 needs AMENDMENT before implementation release.

CONCRETE FAILURE CASES — HOW A NAIVE BUILD SILENTLY CORRUPTS STATE
======================================================================

F1 — “EVIDENCE CONTRACT” BECOMES A MUTATING GOD OBJECT
Draft 1’s Evidence Contract currently lists both definition-time fields and runtime/model fields, including “observed response/artifact” and “learner-estimator/inference-rule version.”
Failure:
- contract is authored before an attempt;
- learner answers;
- implementation adds the response to the contract or clones the contract per attempt;
- estimator changes later, so every contract now appears stale and requires another version.
Result: task definition, learner event and inference model are duplicated in one object; re-versioning one layer fans out through unrelated layers.
Smallest repair: Evidence Contract must be a DEFINITION only: task-version ↔ claim-version mapping, intended evidence role, validity/conditions semantics and mapping rationale/version. Runtime response belongs to Observation. Scorer belongs to ScoreResult. Inference/estimator version belongs to derived Interpretation/Estimate.

F2 — IMMUTABLE ATTEMPT + LATE/REVISED SCORING IS INTERNALLY IMPOSSIBLE
Draft 1 says observations are immutable but examples include “raw/scored result” and “rubric output.”
Failure:
- constructed response is committed at T0;
- score arrives at T1 from human/AI scorer;
- score is appealed/regraded at T2.
A single immutable attempt cannot acquire or replace the later score without mutation.
Smallest repair: split immutable ResponseObservation from append-only ScoreResult. ScoreResult references response ID + rubric/scorer/version and may supersede a prior score result. Learner inference consumes the effective score result, not a mutable attempt row.

F3 — GENERIC RELATION EDGE BECOMES A SCHEMA-FREE GOD GRAPH
Draft 1’s generic relation types include supports, assesses, requires/prerequisite, part-of, related-to, supersedes and derived-from.
Failure:
- Task→Claim “assesses” edge exists;
- separate task→claim Evidence Mapping exists;
- source “supersedes” edge exists;
- separate version lineage also exists;
- “derived-from” duplicates provenance.
Two representations drift and disagree about which relation is authoritative.
Smallest repair: REMOVE universal edge semantics where a dedicated contract already exists. Use bounded relation families with valid endpoint types:
- curriculum outcome ↔ claim alignment;
- claim → claim prerequisite with hard/soft/informational status;
- source/content → claim support where needed;
- task → claim evidence mapping as its own contract;
- version lineage/supersession as dedicated revision metadata;
- provenance/derived-from as provenance metadata.
Do not let one edge table express all of these.

F4 — ITEM REMAPPING CAN DOUBLE-COUNT OR MOVE COMPETENCE BETWEEN CLAIMS
Failure:
- item Q originally maps to Claim A;
- learner answers Q correctly;
- mapping is later corrected to Claim B;
- recomputation creates a new interpretation for B but old A interpretation remains effective.
Result: one attempt becomes evidence for both A and B.
Opposite naive repair is also corrupt: moving old evidence to B automatically may claim competence for a construct the original mapping never validly represented.
Smallest repair: every mapping revision needs explicit retrospective applicability semantics, e.g. FUTURE_ONLY / RETROACTIVE_SAFE / INVALIDATE_PRIOR_INTERPRETATION / HUMAN_REVIEW_REQUIRED. Current estimates select exactly one effective interpretation lineage. Historical decisions keep the mapping version they actually used.

F5 — MULTI-CLAIM TASK FAILURE IS MISATTRIBUTED TO EVERY CLAIM
Failure:
- one engineering/law scenario maps to three claims;
- learner gets the item wrong;
- naive interpretation decrements all three estimates.
The response may not identify which component failed.
Smallest repair: mapping semantics must distinguish component-attributable evidence from JOINT/CONJUNCTIVE evidence. Per-claim negative evidence requires a score/rubric component that actually isolates that claim. Otherwise keep evidence joint/diagnostic and do not manufacture three independent failures.

F6 — SOURCE REVISION CASCADE BECOMES A DESTRUCTIVE INVALIDATION STORM
Draft 1 says source change must identify affected assertions, tasks, mappings, interpretations, estimates and prior recommendations.
Failure:
- instructor fixes punctuation/formatting in a source;
- source version increments;
- naive cascade invalidates every downstream task and learner estimate despite no semantic change.
Opposite failure:
- substantive legal/policy rule changes;
- implementation treats it like cosmetic revision and preserves current evidence authority.
Smallest repair: version lineage must carry change-impact scope or explicit affected dependency selections. Never “invalidate everything downstream by version number.” Historical observations stay under the old authority snapshot; current estimates decide whether old evidence remains comparable under the new semantic version.

F7 — REPLAYABILITY FAILS AFTER MODEL/MAPPING CHANGE
Draft 1 wants material recommendations reconstructable while derived interpretations may be invalidated/recomputed.
Failure:
- recommendation D used Estimate E under model M1 and mapping R1;
- current system later recomputes E under M2/R2 and overwrites the cache;
- decision trace references “learner estimate” but not exact input values/cursor.
Result: old decision cannot be reconstructed.
Smallest repair: decision record must capture exact as-of inputs: observation high-water mark/cursor, catalog/mapping revision, policy config version, model config version, evaluation instant, bounded estimate feature snapshot/digest, candidate shortlist/exclusion codes and random/tie-break seed where used. Derived caches are keyed by model+cursor; they are never silently overwritten as if they were historical truth.

F8 — TWO TABS PRODUCE DUPLICATE “NEXT” DECISIONS
Failure:
- tab A and tab B read same recent recommendation history;
- both generate same next action before either writes history;
- both persist it.
Anti-repetition and recommendation history are now wrong; later estimates may receive duplicated evidence.
Smallest repair: decision request idempotency key + per learner/context monotonic decision sequence or optimistic concurrency token. A stale concurrent request returns the already-accepted decision or recomputes against the new sequence.

F9 — RESPONSE RETRY/DOUBLE-SUBMIT OVERWEIGHTS ONE ANSWER
Failure:
- network retry or double click writes the same committed response twice;
- learner estimator reads two successful observations;
- confidence rises incorrectly.
Smallest repair: client operation/response commit ID with uniqueness constraint; server assigns durable event identity. Idempotent retry returns the existing observation.

F10 — CLIENT CLOCK CORRUPTS RECENCY/RETENTION
Current prototype uses client-side Date/new Date()/Date.now() heavily. That is fine for a local preview, not authoritative Engine v1 chronology.
Failure:
- offline device clock is wrong or changed;
- a newly synced attempt appears older than a prior attempt;
- delayed-retrieval/recency logic produces false memory risk or false “later” evidence.
Smallest repair: store client_occurred_at + clock/source metadata where useful, but also authoritative received_at/server sequence. Estimators define which clock they use. Deadlines carry canonical timezone/instant semantics.

F11 — MISCONCEPTION HYPOTHESIS BECOMES SELF-CONFIRMING
Failure:
- two misses create misconception H;
- policy chooses only tasks designed around H;
- those tasks produce errors;
- H strengthens because the engine selected evidence likely to confirm H.
Smallest repair: hypothesis is DERIVED, never evidence. Persist/mark decision selection context on subsequent observations. Require competing explanations and a disconfirmation/probe path before high-confidence use. Estimator consumes observations/results, not its own prior hypothesis label.

F12 — “PEDAGOGICAL ACTION” TAXONOMY CONTRADICTS ITS OWN BOUNDARY
Draft 1 lists ADVANCE and PAUSE/COMPLETE as pedagogical action families, then states navigation/session control is separate from pedagogical actions.
Failure:
- policy selects PAUSE or ADVANCE as if they are learning interventions;
- implementation now needs a second layer to decide what content/task actually occurs.
Smallest repair: REMOVE session controls from pedagogical action taxonomy. Treat navigation/session operations separately. For beta, keep concrete learning-delivery actions small, e.g. INSTRUCTION/EXPLANATION, WORKED_EXAMPLE, GUIDED_PRACTICE, RETRIEVAL_PRACTICE, ASSESSMENT_PROBE. “Review/remediate/advance” can be intent/reason labels unless they identify a concrete deliverable.

F13 — POLICY HARD CONSTRAINT ACCIDENTALLY BANS TEACHING CONTENT
Draft 1 says item/task must have explicit current claim mapping. That is correct for evidence-producing tasks but not necessarily for an explanation or approved teaching resource.
Failure:
- approved explanation is available and source-grounded;
- it is not an assessment task and has no task→claim Evidence Mapping;
- generic hard constraint rejects it.
Smallest repair: scope evidence-mapping requirements to EVIDENCE-PRODUCING actions. Teaching/resource actions require approved source/content authority + claim relevance, not an artificial assessment mapping.

F14 — PERFECT “IMMUTABILITY” CONFLICTS WITH DELETION/PRIVACY
Failure:
- user/data-retention policy requires deletion of old learner evidence;
- “immutable ledger” is interpreted as physically undeletable;
- decision traces also copied raw response payloads to preserve replay.
Result: privacy requirement cannot be honoured without database surgery.
Smallest repair: “immutable” means append-only/no silent rewrite while retained. Define deletion/redaction/tombstone/cryptographic-erasure semantics. Decision traces store references and bounded derived values, not duplicate raw learner content. After lawful deletion, reconstruction may explicitly degrade rather than secretly retaining deleted evidence.

F15 — CURRENT SINGLE-FILE STATE MODEL TEMPTS THE EXACT SHORTCUT DRAFT 1 FORBIDS
Current prototype synchronously computes correctness and pushes mutable attempt records into local state; attempt objects include question/topic/objective identity and source IDs, and projection/summary code derives learner-facing state directly from those arrays.
Failure if copied into Engine v1:
- objective/claim mapping gets baked into the historical attempt as if factual;
- later remap requires rewriting attempts or leaves stale interpretation embedded in history;
- UI state becomes the learner model store;
- late scorer/retry/concurrency cannot be represented safely.
Smallest repair: future Engine observation stores the task/version and response facts. Claim/KC mapping is a separate versioned authority artifact. Current single-file state remains prototype/UI state; do not grow it into the Engine v1 persistence model and do not add another late sgBase* override layer as the engine boundary.

F16 — DECISION TRACE STORAGE CAN EXPLODE
Draft 1 says record candidates and exclusions for every material decision.
Failure:
- candidate generator sees hundreds/thousands of item/action combinations;
- every recommendation copies every candidate payload and evidence reference.
Storage/privacy costs explode and candidate traces become uninspectable.
Smallest repair: define a bounded evaluated shortlist. Persist selected action, shortlist IDs/types, exclusion reason codes, generator/policy/catalog versions, input cursor/digest and deterministic candidate-generation metadata. Do not duplicate full content payloads per decision.

8. INSTRUCTOR evidence: derived read model/consumer contract, not another authoritative state store.

SMALLEST IMPLEMENTATION-SAFE SKELETON
======================================================================

ONE DEPLOYABLE APPLICATION / ONE RELATIONAL DATA STORE FIRST. Modules are logical boundaries, not services.

A. AUTHORITY / CATALOG MODULE
Durable versioned definitions only:
- source_version
- sparse approved_content_unit/assertion_version
- learning_claim_version
- optional curriculum outcome ref/alignment
- task_version
- rubric/scorer_definition_version
- task_claim_mapping_version
- bounded claim prerequisites/relations
- assessment/assistance policy version
- next-action policy config version
Dedicated version/provenance lineage; no universal relation-edge god graph.
KC is an extension point, not required beta schema.

B. OBSERVATION MODULE
Append-only facts:
- response_commit(idempotency_key, learner/session, task_version_id, action/decision_id, client_occurred_at, server_received_at/sequence, response payload/reference, support/intervention facts)
- score_result(response_id, rubric/scorer/version, score/output, status, supersedes_score_result_id)
Simple deterministic MCQ scoring may be computed immediately but still has explicit scoring-version identity if used historically.
No claim/objective mapping is baked into the observation as learner truth.

C. INFERENCE / READ-MODEL MODULE
Pure derivation over A+B:
- interpret evidence under mapping/inference version;
- emit atomic claim contributions or joint evidence records;
- estimate learner state as-of observation cursor/model config;
- cache by `(learner, claim, cursor, model_config)` if needed.
No policy outputs feed back as evidence.
Derived interpretation rows, if persisted for performance/audit, carry derivation_run_id and are replaceable caches, not primary truth.

D. DECISION MODULE
Pure decision request input:
`{learner/context, evaluation_time, observation_cursor, catalog_revision, estimator_config, policy_config, learner_goal_ref, assessment_policy_ref, expected_decision_seq}`
Pipeline:
1. generate bounded available concrete action candidates;
2. apply hard constraints;
3. apply lexicographic/small priority rules;
4. deterministic/tie-break selection;
5. persist DecisionRecord atomically using request idempotency + expected sequence.
DecisionRecord stores selected action version/ref, bounded shortlist + exclusion/reason codes, exact input version/cursor refs, feature digest/snapshot needed for reconstruction and random seed if used.

E. APPLICATION / EXECUTION MODULE
- renders/delivers the selected task/content;
- owns session/navigation controls separately from the pedagogical action taxonomy;
- user action creates new Observation referencing the triggering decision/intervention.
Current StudyGrid shell/router can later call this boundary, but Engine v1 must not be implemented as another mutable global-state/late-render override layer.

F. INSTRUCTOR READ MODEL
Derived aggregation over authoritative catalog + observation/inference data.
Observation → hypothesis → possible action presentation.
Only instructor approvals/actions that confer new authority become durable writes back into A or explicit action records.

ADDITIONAL FALSIFICATION TESTS TO ADD BEFORE IMPLEMENTATION RELEASE
======================================================================

1. IDEMPOTENT RESPONSE RETRY — same response commit sent 5x produces exactly one observation/evidence contribution.
2. CONCURRENT NEXT ACTION — two tabs requesting “next” from same decision sequence cannot both create distinct accepted decisions from stale history.
3. LATE SCORE — response exists before score; estimate changes only after effective score result arrives; observation row never mutates.
4. REGRADE — new score supersedes old; current estimate counts one effective score lineage, old decision remains reconstructable under old score version.
5. REMAP A→B — mapping correction cannot make one attempt count for both claims; retrospective applicability is explicit.
6. MULTI-CLAIM WRONG ANSWER — failure without component rubric does not automatically lower every mapped claim.
7. SOURCE COSMETIC REVISION — formatting-only source revision does not invalidate learner evidence.
8. SOURCE SEMANTIC REVISION — affected tasks/mappings can be identified; old observations stay historical; current estimate applies explicit comparability/invalidation rule.
9. MODEL UPGRADE — M2 estimate may differ from M1 without altering the M1 decision record/reason reconstruction.
10. POLICY SELF-CONFIRMATION — misconception-guided probe does not treat the prior hypothesis/policy selection as independent evidence.
11. CLOCK SKEW/OFFLINE SYNC — client timestamps cannot silently reorder authoritative evidence used for delayed-learning logic.
12. PRIVACY DELETE — deleting retained learner evidence does not leave raw duplicate content in decision traces; old trace reports reduced reconstruction.
13. STALE AUTHORITY DURING DECISION — source/mapping policy changes mid-request either produce an explicitly old-snapshot decision or trigger a retry under the new revision; never a hybrid.
14. CANDIDATE TRACE BOUND — thousands of available tasks do not create unbounded duplicated decision payloads.
15. CURRENT-PROTOTYPE SHORTCUT — future engine test proves raw observation does not persist current `objectiveId`/claim inference merely because the UI question object contains it.
