1. H2 — CROSS-INSTANCE FRESHNESS RESIDUAL
======================================================================

VERDICT: REPRODUCED-SRC.
SEVERITY: P1 CONFIRMED.

Why the baseline fails:
1. VisitStore.create builds every run with `previouslySeen = seen.has(taskId)` using receipts/exposure as they exist at plan-creation time.
2. markShown later records actual presentation in `state.exposure[taskId].shownIn` without revising already-created run.previouslySeen.
3. submit reads live help flags from exposure, but sets `support.previouslySeen` from the stale run.previouslySeen snapshot.
4. attempt 1 + no help + stale previouslySeen=false can therefore satisfy the `fresh` predicate.
5. provider submit treats support.previouslySeen=false as unhelped and can return evidence=clean/fresh=true.

Concrete ordinary witness on current content:
- Default READY `bio-u2-quiz` includes `osm-m1` because the checkpoint covers diffusion+osmosis and standard READY round-robins fresh task groups.
- Start READY, advance to first question and pause. Its later `osm-m1` run exists with previouslySeen=false but has not yet been shown.
- Start NEW Osmosis. Its authored memory tasks include `osm-m1` and `osm-o1`. Reach Try From Memory, show `osm-m1`, do not answer it, then pause.
- Resume the original READY instance, complete the preceding READY question, reach `osm-m1` and answer it correctly first try.
- By then exposure for `osm-m1` contains the NEW instance and then the resumed READY instance, but the READY run still carries previouslySeen=false from creation.
- Baseline submit therefore permits support.previouslySeen=false, fresh=true and provider evidence=clean even though the same task was already presented in another instance.

Impact:
This is not cosmetic metadata. Clean/fresh receipts feed learner feedback, completion summaries, group coverage and Progress. A cross-instance presentation can be misrepresented as independent evidence. P1 is the correct classification.

H2 FIX CONTRACT / INVARIANT
At the evidence boundary, `previouslySeen` must reflect any presentation or accepted answer of the same task in a DIFFERENT session instance that occurred before this submit, including events after this plan was created. The current instance's own first display must not by itself make the first attempt nonfresh. History/receipts/exposure must never be cleared to manufacture freshness.

3. H1 — UNRELATED ELIGIBILITY-REVISION STRANDED CHECK
======================================================================

VERDICT: REPRODUCED-SRC.
SEVERITY: P2 CONFIRMED ON CURRENT REPAIRED IA.

Why the baseline fails:
1. submit captures the current global `envelopeRevision`, then sets the run to phase=checking with pendingOp.
2. Every Teaching eligibility setter calls reviseEnvelope, which increments ONE global envelopeRevision before checking whether an unfinished session is actually affected.
3. For an unrelated Teaching change, the Biology session remains eligible/unblocked and its generation/pendingOp are untouched.
4. When the provider later resolves OR rejects, matches() fails solely because global envelopeRevision changed.
5. Both the try and catch branches return stale immediately on that mismatch. Neither branch clears pendingOp nor restores phase=locked.
6. Result: eligible session, blocked=false, zero new receipt, but run remains checking with pendingOp; resubmit cannot run because resubmit requires locked.

Concrete witness:
- Start a Biology learning session and commit a valid guided answer; choose confidence so provider submit is pending.
- While pending, call an unrelated Math Teaching mutation such as confirming `math-eq-check`.
- Biology eligibility remains valid, but global envelopeRevision advances.
- Settle the original Biology provider submission.
- Baseline matches() rejects it as stale and returns without cleanup, leaving checking/pendingOp stranded.

No-op amplification:
The current Teaching setters do not compare effective old/new values before revising. Calling setReleased/math-w5=true, setSourceStatus/src-math-balance=approved, setCheckpointConfirmed/math-eq-check=false, or shareStudySet(..., false) can still advance the global revision even when the effective value is unchanged, so a semantically no-op call can trigger the same stranded state.

Why P2, not P1, on the current repaired product:
Current ordinary full-page Teaching navigation generally pauses an active learning session before a teacher mutation, and pause already retires a checking run to locked. So the controller bug is real but its direct current-UI incidence is narrower than H2. P2 is appropriate for this baseline. If an integrated Codex/hardening UI makes Teaching/role mutations reachable alongside an active check and reproduces the dead-end in an ordinary path, that integrated functional defect becomes release-blocking regardless of the historical label.

H1 FIX CONTRACT / INVARIANT
A policy/version change may never leave a settled operation permanently in checking. Two implementation families are acceptable:
A. scope policy invalidation so unrelated changes do not invalidate the pending operation; or
B. keep broader invalidation but retire invalidated pending work to a truthful recoverable locked state.

Do NOT simply remove stale/version fencing. Relevant revocation/reset/restart/pause must still prevent obsolete results from being applied.
