1. H2 — CROSS-INSTANCE FRESHNESS RESIDUAL
======================================================================

VERDICT: REPRODUCED.
SEVERITY: P1 CONFIRMED.

Causal source path:
1. `VisitStore.create()` computes one `seen` set from receipts + exposure at plan creation.
2. Every planned run snapshots that moment into `newRun(id, seen.has(id))` / `run.previouslySeen`.
3. `markShown()` later adds the same task to live exposure for whichever instance actually presents it.
4. An already-created run in another instance is not revised when this later exposure occurs.
5. `submit()` reads live hint/reveal/anotherWay flags but sets `support.previouslySeen` from stale `run.previouslySeen`.
6. `fresh` is then allowed when attempt===1, support.previouslySeen===false and no other help exists.
7. Provider evaluation can therefore emit `evidence=clean` / `fresh=true` after the task was already shown in another instance.

Ordinary current-fixture witness:
- Biology checkpoint `bio-u2-quiz` covers diffusion + osmosis.
- NEW Osmosis memory includes `osm-m1` and `osm-o1`.
- READY planning draws from those learning groups and can include `osm-m1`.
Sequence:
A. Create READY and pause before `osm-m1` is shown; its run has previouslySeen=false.
B. Create NEW Osmosis, reach memory, present `osm-m1`, do not answer, pause.
C. Resume READY, reach `osm-m1`, answer correctly first try without help.
At C, live exposure records another instance but READY's snapshot remains false, so baseline source permits false clean/fresh independent evidence.

Impact:
Clean/fresh receipts feed feedback wording, completion counts, bounded coverage/Progress and future recommendations. This is a learning-integrity overclaim, so P1 is correct.

H2 invariant after issue #4:
At submit/evidence boundary, prior exposure must be computed from accepted receipts and actual presentation/help history across OTHER instances up to that moment. The current instance's own first display must not make its first attempt nonfresh. Plan creation must not freeze a claim that later exposure can invalidate. No receipt/history/exposure may be erased to manufacture freshness.

3. H1 — UNRELATED ELIGIBILITY REVISION STRANDS SETTLED CHECK
======================================================================

VERDICT: REPRODUCED.
SEVERITY: P2 CONFIRMED ON CURRENT IA.

Causal source path:
1. `submit()` captures global `envelopeRevision`, sets run `phase='checking'`, stores `pendingOp` and awaits provider result.
2. Every `setReleased`, `setSourceStatus`, `setCheckpointConfirmed` and successful `shareStudySet` calls `reviseEnvelope()`.
3. `reviseEnvelope()` increments the one global revision even when the changed scope is unrelated to the active session and that session remains eligible.
4. It only calls `block()` for sessions that are now ineligible. An unrelated still-eligible session stays `checking` with the old pendingOp.
5. When provider resolve/reject settles, `matches()` rejects it solely because captured revision != current revision.
6. submit catch/success then returns `stale` without clearing the still-current run's `checking` phase or `pendingOp`.
7. `resubmit()` requires `phase='locked'`, so there is no truthful in-place retry until some separate lifecycle action such as pause occurs.

Concrete current-fixture witness:
- Begin a delayed Biology answer after response/confidence are committed.
- While provider is pending, confirm unrelated Math checkpoint `math-eq-check` or make another unrelated eligibility mutation.
- Biology remains eligible, but global revision changes.
- Provider settles.
Baseline source returns stale and can leave `phase=checking`, original pendingOp, blocked=false, zero receipt.

Impact/severity:
The defect strands a controller transaction but does not itself accept false learning evidence. Current IA limits ordinary incidence because many workspace transitions pause the active session. P2 is correct for the present candidate. If later integration makes this dead-end routinely reachable, it remains release-blocking even if severity label stays P2.

H1 invariant after issue #4:
Stale-safety must remain. An unrelated eligibility change may either (A) leave the pending operation valid so it settles normally, or (B) explicitly retire that operation to a truthful recoverable state. It must never leave a settled current run permanently `checking` with stale pendingOp. Recovery must preserve committed response/confidence and must not accept obsolete work after a relevant revocation.
